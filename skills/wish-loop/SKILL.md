# wish-loop · 许愿闭环

用户说的是「想要什么」，不是「怎么改」。你要自己把愿望翻译成可执行、可验证、可交付的东西。

## 什么时候加载

- 一句话描述一个功能/页面/脚本，没给实现细节。
- 一次改动跨 3 个以上文件，或跨技术栈。
- 上一轮返工过：你说做完了，用户说不对。

单点小改（改文案、修一行判空）不用加载，直接改。

## 阶段 0 · 判愿（30 秒，不写码）

从一句话里抽出三件事：

| 抽什么 | 缺失时怎么办 |
|---|---|
| **谁**在什么场景用 | 按最像真实用户的那个场景定，写进「已假设」 |
| **什么可观察的结果**算做到 | 定不出来就先定义观测点（命令输出/页面元素/文件内容） |
| 验收能否**机器判定** | 不能 → 先做阶段 2，把判据变成可执行的 |

三个红线开关，命中才能问一句（其余一律自己拍）：

1. 会删除或覆盖用户已有数据（不是自己刚生成的文件）。
2. 需要账号、密钥、付费、外部审批。
3. 两种做法代价差 10 倍以上且不可兼得（比如换框架 vs 打补丁）。

问的时候只问一句，并给出你的默认选项：「我按 A 做，除非你要 B」。有明确 A/B 二选一用 `ask_user_question`（第一项写推荐默认）；否则在回复里直接问一句，别弹结构化问题。

## 阶段 1 · SPEC（8~20 行，不写实现）

落盘到 `<项目根>/.wish/<slug>.md`（隐藏目录，不污染仓库；用户明确说别建文件就只在回复里给这 20 行）。SPEC 头加一行「本文件可删」。

```markdown
# WISH: <一句话>

目标：<用户能看见的结果，一句话>

可见行为：
- 打开/运行 X，做 Y，应看到 Z
- 失败时看到 <错误提示/退出码>

验收（可执行）：
- `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\verify.ps1` → 退出码 0，最后一行打印 OK（本机只有 powershell.exe 5.1，没有 `pwsh`；.ps1 不带 `-ExecutionPolicy Bypass` 会被拒，见 verify-harness §2）
- `<单测命令>` → 0 failed
- <UI 类：截图/元素存在性检查>

不可变量：技术栈 / 目录结构 / 现有公开 API 形状 / 不许动的文件

已假设：<自己拍的决定，逐条，一条一行>

非目标：<明确不做的事，防止范围蔓延>
```

SPEC 的价值不是文档，是**把「做完了」变成可反驳的命题**。

**它是抗压缩的锚**：那条「许愿：…」的用户消息在长会话里可能被折叠成摘要，之后每轮一律以 SPEC 文件为准，不以对话记忆为准——被压缩掉的细节回去读文件，别凭印象补。

## 阶段 2 · 验收先行

- 先写 `scripts/verify.ps1`（或 `.sh` / `npm test` 入口），跑一次，确认它**红**。
- **接手已有改动**（本会话已改过东西、或工作区有未提交改动）：先跑一次验收记**基线**——当前绿的写进 SPEC 的「基线」段，验收判据必须能区分「我改出来的」与「本来就绿的」。否则一开跑就绿，等于假绿放行。
- 红的理由必须是「功能还没做」，不能是「脚本写错」。脚本自身错误先修脚本——判据是它在空实现上打的是断言失败，不是 `Pattern is null` / `CommandNotFoundException` / 乱码（`.ps1` 含中文却没 BOM 时 PS 5.1 会按 GBK 解码，见 verify-harness §2）。
- 一条命令 + 退出码 + 一行摘要。不要靠人肉看日志判断。
- 判据分级、脚本模板、退出码陷阱见 skill `verify-harness`。

没有可执行的验收就进入实现 = 许愿变许瞎。

## 阶段 3 · 最小实现

- 只做让**第一条验收变绿**的最小改动，别一次铺满全功能。
- 一次动一个关注点：先让它跑起来，再让它对，最后让它好看。
- 同一文件第 3 次 `edit` 失配 → 整块 `write` 覆盖（文件 <80 行），或先 `read` 出唯一锚点再 `edit`；确需批量替换时用 pwsh 脚本，但必须在同一步断言命中数 = 期望值（`(Select-String … ).Count -eq N`），不等就回退重来。
- 任何 `edit` 前该文件必须已 `read`（注入的 AGENTS.md / NOTES.md 不算读过）。
- 源码只用 `write`/`edit`，禁止用 shell 重定向写源码（编码、BOM、换行会坏）。

## 阶段 3.5 · 扇出编码（`subagent`）

愿望拆成几块**互不重叠**的编码活时，派子代理并行做能省墙钟；但每次派发 = 一次冷前缀 + 一份任务书，门槛要卡死。

**派（三条同时成立）**：

- ≥2 个切片，每个都能独立交付、独立验收（各自一条命令能判绿）；
- 写域不重叠（各自允许改的文件/目录互不相交）；
- 每块都值一次冷启动（>30 行改动、跨文件、或要跑一遍构建）。

**不派**：单文件/单点改动；几块耦合在同一批文件（写域重叠只能串行，串行不如自己顺着做）；需要主会话上下文才能推断的（子代理看不到本会话，也看不到你怼 SPEC 的过程）；预算紧（子任务墙钟同样计入 40 步 / 15 min）。

**任务书六项，缺一不可**（子代理是全新上下文，只继承预设的 persona/技能/工具，不继承对话）：

1. **目标**：一句话，做完之后「谁看见什么」。
2. **写域**：允许改的路径白名单 + 「其他只读」；点名哪些文件归它，别和并发的另一块重叠。
3. **现有事实**：工程根、构建/验收命令**原文**（含 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File`）、环境坑（PATH 里可能没有 `node`，给绝对路径；BOM；退出码别用 `cmd; echo EXIT=…` 洗掉）。让它照原文跑，不自己猜。
4. **已完成到哪**：父会话已做的部分（`文件:行`），避免重复实现或覆盖。
5. **只做一件**：下一步只做哪一件事 + 步数上限（如 ≤15 步）+ 一句「不许再派子代理」。
6. **完成判据**：哪条命令退出 0 算完 + 回报格式固定三行（改动 / 验证 / 残留）。

派发要点：

- 一次调用派一块；互不依赖的几块在**同一条消息**里一起发起，别串着等。
- 显式给 `cwd`（工程根），别让它继承你当前所在目录。
- 不轮询：发起后继续干自己那块（写总验收、复核不可变量），完成通知会自己回来。
- 子代理自身也挂着 `subagent` 工具，但深度上限是 1（配置 `maxDepth: 1`），到顶会被提示「直接做」；任务书里写明这一条省它一次试错。

收活：

- 子代理报绿不算绿 —— 合并后**父 agent 自己跑一次总验收**。
- 先 `git diff --stat` 核对它有没有越界改文件；越界就回退再谈，别在越界的树子上继续叠。
- 中断、半成品、同一错误复现 → 阶段 4.5。

## 阶段 4 · 循环

```
跑 verify → 只读第一处失败 → 改一处 → 重跑
```

- 失败输出只取关键行：编译取错误行（含中文「错误:」），测试取 failed 名 + 断言行，构建取 `BUILD FAILED` 前后 3 行。从 `$env:TEMP\wish-verify\<工程名>.log`（仓库外，交付不用清；若首行写 `TEMP unwritable` 说明沙箱不让写 TEMP，日志在 `<工程根>\.wish\verify.log`）用 `Select-String -Pattern 'BUILD FAILED|错误:|\[ERROR\]' -CaseSensitive` 取，别肉眼看全量。
- **三振法则**：同一处失败连 3 次，停手写一句「换法：X→Y」再动。换法必须换假设（换 API、换路径、换库、换设计），不是换个写法重试。
- 攒 3~5 处改动跑一条合并验证，不要每改一行跑一次全量构建。
- 成功跑过的命令不重跑；要确认状态就查产物文件时间戳。
- 版本/环境类失败先看事实：`node -v`、`java -version`、`where x`，别猜。

## 阶段 4.5 · 子任务中断就续，不重派

派发判据与任务书写法见阶段 3.5；这一节只管派出去之后停下来的情况。

扇出（`subagent`）之后，子任务可能中途停：返回里写「中断 / incomplete」、`list_agents` 里 inactive 却没有最终结论、产物写了一半（文件末尾截断、verify 没跑）、或者这次报的错和上次一样。

处置顺序，别跳步：

1. **先续，不重派**：`send_message({ agent: '<name>', message: '<断点包>' })`。子任务保留着自己的上下文；重派等于把探索重做一遍，还很可能撞同一个坑。
2. **断点包必含六项**（它自己的上下文可能已被压缩，摘要里未必还有这些）：目标一句话 / 已完成到哪（`文件:行`、已绿的检查）/ 卡点原文（报错那一行照抄）/ 下一步只做一件事 / 写域（哪些文件归它，别和别人重叠）/ 完成判据（哪条命令绿了算完）。只说「继续」等于让它猜。
3. **续两次不动就换法**：同一子任务连续 2 次 `send_message` 仍无进展 → `interrupt_agent` 收尾（别留僵尸进程），父 agent 自己接手，或拆小后重派一个写域明确的新子任务。这就是铁律 4 的三振在子任务上的形态。
4. **写域冲突就串行**：两个子任务动同一批文件 → 前一个交付后再派后一个；并行只在写域不重叠时成立。
5. **子任务的「我跑通了」不算绿**：合并时父 agent 自己跑一次总验收（`scripts/verify.ps1`）。子任务自报绿是假绿的第二大来源——它看不到别人的改动，也可能只验了自己那一块。

等子任务的墙钟同样计入 40 步 / 15 min 预算；撞线就交「已绿 / 红项 / 下一步」，别在原地续命。

## 阶段 5 · 交付

**先跑阶段 5.5 清理，三行在清理之后才发。**

回复只留这些：

```
改动：<文件:行> — <≤10 字理由> ｜清理：删 N 留 M（<留下的判据资产>）
验证：<命令> → <结果一行>
残留：<没验到的 / 需真人真机的 / 已知限制>
```

- 没跑过的检查，不许写「已验证」。
- 许愿产出是**独立文件**（文档/视频/图片/表格/报告）→ 用 `present` 交付给用户（附路径与一句话说明）；纯代码改动留在工作区，不 present。
- 交付前自检：
  1. SPEC 每条验收都跑过？
  2. 不可变量动过吗？（技术栈、目录、公开 API）
  3. 跑过阶段 5.5 清理了吗？删了几个、留了什么，写进「改动」行（没删就不写这一段）。
  4. 用户拿到手第一步能不能直接跑？（命令写清楚）

## 阶段 5.5 · 清理过程文件（交付的最后一步）

「做完了」包括现场干净：交到用户手上的工作区里，不该有你自己造的过程件。但清理不是 `rm -rf` 一把梭——先分类，再逐条删。

**按改动规模分档，别给小改套大流程**：本轮只改 1 个已有文件、没新建任何文件 → 不必跑三步清点，只要确认自己没留临时件；**没删东西就不用重跑验收**（铁律 5 的「删后仍绿」只在真删过时生效），三行也不必写清理列（见 verify-harness §7）。只要新建过文件、跨 3 个以上文件、或用过截图与 codegen → 走完下面三步。

| 类别 | 典型文件 | 处置 |
|---|---|---|
| 判据资产 | `scripts/verify.ps1`、`scripts/smoke.mjs`、`.wish/<slug>.md` | **留**：交付三行的「验证」要引用脚本；SPEC 是可复跑的依据（用户没要求留档可删） |
| 纯过程件 | `*.log`、`*.bak`/`*.orig`、截图 dump、一次性 codegen 脚本、`.tmp-*`/`scratch/`、注释掉的旧实现、试到一半的备用实现 | **删** |
| 用户资产 / 重建昂贵 | 源码、`node_modules`、`dist`/`build`/`target`/`.venv`、`.git`、用户原有文件 | **永不删** |

三条命令，别凭记忆：

1. **先清点，只打印不删**：仓库内 `git status --porcelain -uall`（**`-uall` 不能省**：不加时 git 把整个未跟踪目录折成一行 `?? .wish/`，根本看不出里面有哪些文件）；无 git 时只扫一层再下钻：`Get-ChildItem -Force | Where-Object Name -notin 'node_modules','dist','build','.git'`，然后 `Get-ChildItem -Force .wish,scripts` 这类候选目录。别用 `-Recurse ... -Exclude node_modules`：`-Exclude` 不过滤遍历，只过滤列出的项，实测 `-Exclude .git` 仍会把 `.git\hooks\*` 全打出来。对着上表逐行标「留/删」。条目上百行时先 `Select-Object -First 50` 看主干，别把整屏灌进上下文。
2. **核对绝对路径 + 归属**：每个待删路径先 `Resolve-Path`，确认①在本工程内 ②是本轮自己生成的 ③不属第三类。判定"是不是本轮自己造的"以**本轮对话与 SPEC 里出现过的路径**为准；清点结果里对不上号的（用户原有的未跟踪文件、`vendor/`、别人留下的脚本）一律不删，写进「残留」。任一条不确定 → 不删。
3. **逐条删 + 复核**：`Remove-Item -LiteralPath <路径> -Recurse -Force`（一条一个路径，不用通配、不用 `-Include`）；删完 `git status --porcelain -uall` 应只剩本轮改动文件，再跑一次验收命令 → 仍 `OK`。复核不是走过场：删掉 `src/` 里一个被 import 的文件，`verify.ps1` 立刻 `exit 1`（实测 `Cannot find module`），这就是它拦住「清理过头」的方式。

边界：

- 自己刚生成的过程件不用问（红线 1 管的是**用户已有数据**）；用户原有文件、别人（含子任务之外）的产物一律不动。
- **删完必须重跑验收**：删掉一个还被 import 的临时模块，「全绿」就成了历史，交付时是假的。
- 验收脚本的日志默认写 `$env:TEMP\wish-verify\`，本来就不在仓库里，不用清；别把它改回仓库内。若脚本首行写 `TEMP unwritable`（沙箱是 `workspace-write`，TEMP 在写域外），日志回落到了 `.wish\verify.log`，那就随 `.wish/` 一起清。
- `.wish/<slug>.md` 若用户没要求留档，连目录一起删，并在三行里说一句。项目是 git 仓库且 `.gitignore` 没忽略 `.wish/` 时，只在「残留」行提一句建议，别自己去改用户的 `.gitignore`（那是改用户已有文件）。
- 交付三行的「改动」行末尾补清理数：`改动：src/a.js:12 修空值 ｜清理：删 3 留 2（verify.ps1、.wish SPEC）`。

## 阶段 6 · 沉淀

- 项目新事实（构建命令、环境变量、坑）→ 写进项目根 `AGENTS.md`，一句话一条。**只留 ≤60 行 / ≤8KB 的常驻事实**（它整份注入上下文，超了早期条目被静默截断）；细节、历史、一次性踩坑写 `NOTES.md`。
- 这次踩的坑、做出的决策 → 写进项目 `NOTES.md`。
- 不改 persona、不改技能，除非用户要求。

## 常见退化与对策

| 退化 | 症状 | 对策 |
|---|---|---|
| 先说后做 | 回了一大段「我将要实现…」然后没动 | 计划超过 3 行就落盘成 SPEC 文件，回复里只留一句「按计划执行」 |
| 假绿 | 把「代码写完」当验收通过 | 只认命令退出码与断言输出；没有就补，不许口头通过 |
| 范围蔓延 | 顺手重构、顺手格式化、顺手升级依赖 | 一次只改一行 SPEC 对应的东西；想顺手做的记进「非目标之外」，交付时问一句 |
| 整文件重写 | 每次改动都 `write` 整个文件 | 优先 `edit` 唯一片段；整写只在重构或文件 < 80 行时 |
| 反复试探 | 同一条命令换个写法试 5 次 | 三振法则；第 3 次去读 `node_modules/<pkg>` 里的 README 与类型定义、`<tool> --version` 实测、或报错码原文（本机无联网检索） |
| 交付即失联 | 说完了但没给怎么跑 | 固定三行：改动 / 验证 / 残留 |
| 现场不干净 | 交付后仓库里多出 `verify.log`、`*.bak`、截图、`.wish/` 里的草稿 | 阶段 5.5：先 `git status --porcelain -uall` 清点，逐条删，删完重跑验收；顺手把日志挪到 `$env:TEMP` |
| 过度提问 | 每个小选择都来问 | 只有红线三问；其余写「已假设」，用户不满意会自己说 |
| 为并行而派 | 单文件小改也开子代理，冷前缀 + 任务书比自己做还贵 | 阶段 3.5 三条门槛同时成立才派；写域重叠一律串行 |

## 自检清单（交付前逐条过）

- [ ] SPEC 存在，且验收是可执行命令
- [ ] 验收曾经红过，现在绿
- [ ] 不可变量没动
- [ ] 新增依赖 = 0（或已在 SPEC 里写明）
- [ ] 阶段 5.5 已跑：过程件删了、判据资产留了，清理数写进「改动」行
- [ ] 交付三行齐
- [ ] 没撞预算线（>40 步或 >15 min 未见绿就该停手交状态，而不是继续磨）
