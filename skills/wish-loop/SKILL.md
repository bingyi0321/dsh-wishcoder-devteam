# wish-loop · 许愿闭环

用户说的是「想要什么」，不是「怎么改」。你要自己把愿望翻译成可执行、可验证、可交付的东西。

## 什么时候加载

- 一句话描述一个功能/页面/脚本，没给实现细节。
- 一次改动跨 3 个以上文件，或跨技术栈。
- 上一轮返工过：你说做完了，用户说不对。

单点小改（改文案、修一行判空）不用加载，直接改。

## 五段流水线（先定谁做，再动手）

一句话愿望拆五段，**段与段之间只靠文件交接**（子代理看不到本会话，也看不到你怎么想的）：

| 段 | 谁做 | 产出 | 交接物 |
|---|---|---|---|
| **1 需求转译** | 本会话加载 `requirement-translator` | 需求卡（给用户）+ SPEC + 分派表（写域/AC/blocked_by） | `.wish/<slug>.md`（含分派表与验收指纹） |
| **2 分派 + 实现** | 每个写域派一个领域 agent 作子智能体（`web-platform`/`android-app`/`win-desktop`/`embedded-firmware`/`debug-research`；深度 1；域内 ≥2 个独立文件块时可再下派一层，深度 2 不可再派） | 代码，逐条把验收跑绿 | 三行回报 + 每次 verify 的关键行 |
| **3 验收** | 派一个**只读验收子代理**（加载 `acceptance-verifier`；单文件小改可 lead 自验，见阶段 4.7） | AC→证据对照表 + 放行/打回 + `TEST-REPORT.md` | 验收结论 + 指纹核对结果 + 报告 |
| **4 功能测试** | 本会话（验收同一轮的最后一步） | 构建→启动→3~5 条主路径（含一条错误路径） | 一轮测试日志 + `EXIT=` |
| **5 三振/收尾** | 本会话 | 改 SPEC/验收、换路线、或亲自写关键 20%；两关全绿后三行交付 | 结论写回 SPEC 的「已知失败」段 |

**段 2 用的是同一个模型，不是更便宜的模型。** 子代理路由受 Session 的 `subagent/model-selection-policy` 约束（`dsh-tool-subagent/lib/index.js:85` `assertAllowedModelSelection`）：没有记录 policy 时，**显式选择只允许等于父路由**，传别的 `provider/model` 直接抛 `child LLM route ... is not allowed for this Session ... explicit selection is limited to the parent route`。该 policy 是会话级持久状态（`stateVersion 1`、`init: null`，由官方 `subagent-model-selection-settings` 行在 profile 层、`agent/created` 时写入，白名单内容即设置页「子代理白名单」里排好的顺序）；白名单内的路由可显式分派，白名单外的仍抛 `child LLM route ... is not allowed for this Session`。

所以派子代理买到的是：**判据解释权被隔离**（实现者不能改验收）+ 一条干净的上下文，**不是省钱**。r1 实测：同一判据、同一任务，派子代理 ≈$0.0100 / 8 请求，本会话自写 ≈$0.0039 / 4 步——**派发更贵**。什么时候还值得派，见「阶段 3 · 执行者」的判据门槛。

六条铁律：

1. **段 1 不写实现。** 转译只出需求卡 / SPEC / 分派表；写代码是段 2 的事，边转译边改文件是自证需求。
2. **段 2 不许改验收。** 实现者只读 `scripts/verify.ps1` 与 `.wish/<slug>.md`，不许 `write`/`edit` 这两个文件。验收指纹（§阶段 1）用来核对；被改过 = 这一段作废，回段 1 重写验收。
3. **一域一子智能体，可再下派一层。** 分派表一行 = 一个领域 agent 子智能体 = 一个写域（深度 1）；该域写域还能切成互不相交的 ≥2 块时，领域 agent 可再下派一层执行子智能体（深度 2，配置 `maxDepth: 2`），**深度 2 不许再派、直接做**。写域重叠就串行，不并行。
4. **段 3 只读且独立。** 验收不改源码、不改验收；判据本身有问题就标「判据缺陷」交回 lead，自己不动手。独立性靠**换一个上下文**（只读子代理）实现，不是靠自觉——`acceptance-verifier` 是规则，不是隔离。
5. **两关都过才算完成。** 验收放行 + 功能测试一轮通过；任一关红只报真实状态（已绿 / 红项 / 下一步），不许把验收绿说成功能可用。
6. **一次规划、多次实现，别横跳。** 每开一个新上下文（子代理或换会话）都是一次冷前缀重付（本机基线 58,828 input/步，单次冷启实测到过 152,286）。段 1→2、段 2→3 各交接一次；规划错了回段 1 改文件，不在段 2 里现场改验收。

为什么这么分：段 1 是判断题、段 3 是接管判断题，都只有本会话能做（子代理没有改 SPEC 的权限）；段 2 是"照判据跑绿"的执行题，谁做都行，**但派出去要付一次冷前缀 + 交给一个看不到本会话的上下文**。本机价目（opencode-go，$/1M）：单会话一个模型跑到尾最省。想让实现段便宜，只能换会话路由本身（比如整场跑 flash），不能在 spawn 时点菜——见上面「段 2 用的是同一个模型」。

## 阶段 0 · 判愿（30 秒，不写码）

段 1 的动作：加载 `requirement-translator`，按它抽观测点 / 定判据 / 定写域 / 定顺序。下表是转译时的判断口径。

从一句话里抽出三件事：

| 抽什么 | 缺失时怎么办 |
|---|---|
| **谁**在什么场景用 | 按最像真实用户的那个场景定，写进「已假设」 |
| **什么可观察的结果**算做到 | 定不出来就先定义观测点（命令输出/页面元素/文件内容） |
| 验收能否**机器判定** | 不能 → 先做阶段 2，把判据变成可执行的 |

三个红线开关，命中才能问一句（其余一律自己拍）：

1. 会删除或覆盖用户已有数据（不是自己刚生成的文件）。
2. 需要账号、密钥、付费、外部审批。
3. 两种做法代价差 10 倍以上且不可兼得（比如换框架 vs 打补丁）。

问的时候只问一句，并给出你的默认选项：「我按 A 做，除非你要 B」。有明确 A/B 二选一用 `ask_user_question`（第一项写推荐默认）；否则在回复里直接问一句，别弹结构化问题。

**主线自己也要先规划**（各 agent 收到任务都先规划，lead 不例外）：动手前先定 4 行——①做什么（目标一句话 + 落的文件）②用什么工具/命令验③派不派子代理、为什么④取舍：为什么选这条路线、代价是什么（被否掉的方案一句）。写不出这 4 行 = 愿望还没转译好，回段 1。

## 阶段 1 · SPEC（8~20 行，不写实现；末尾附分派表）

落盘到 `<项目根>/.wish/<slug>.md`（隐藏目录；同目录写一份 `.gitignore`，内容一行 `*`，用户仓库不出未跟踪噪音；用户明确说别建文件就只在回复里给这 20 行）。SPEC 头加一行「本文件可删」。

```markdown
# WISH: <一句话>

目标：<用户能看见的结果，一句话>

可见行为：
- 打开/运行 X，做 Y，应看到 Z
- 失败时看到 <错误提示/退出码>

验收（可执行）：
- `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\verify.ps1` → 退出码 0，最后一行打印 OK（本机只有 powershell.exe 5.1，没有 `pwsh`；.ps1 不带 `-ExecutionPolicy Bypass` 会被拒，见 verify-harness §2）
- `<单测命令>` → 0 failed
- <UI 类：截图/元素存在性检查>

实现者：<本会话自己 / subagent:<name>（同路由）>　段位：<1 判愿｜2 实现｜3 接管>
验收指纹：<`(Get-FileHash scripts\verify.ps1 -Algorithm SHA256).Hash` 前 16 位>（实现段只读；交付前父侧重算核对）

不可变量：技术栈 / 目录结构 / 现有公开 API 形状 / 不许动的文件

已假设：<自己拍的决定，逐条，一条一行>

非目标：<明确不做的事，防止范围蔓延>
```

SPEC 的价值不是文档，是**把「做完了」变成可反驳的命题**。

**它是抗压缩的锚**：那条「许愿：…」的用户消息在长会话里可能被折叠成摘要，之后每轮一律以 SPEC 文件为准，不以对话记忆为准——被压缩掉的细节回去读文件，别凭印象补。

## 阶段 2 · 验收先行

- 先写 `scripts/verify.ps1`（或 `.sh` / `npm test` 入口），跑一次，确认它**红**。
- **接手已有改动**（本会话已改过东西、或工作区有未提交改动）：先跑一次验收记**基线**——当前绿的写进 SPEC 的「基线」段，验收判据必须能区分「我改出来的」与「本来就绿的」。否则一开跑就绿，等于假绿放行。
- 红的理由必须是「功能还没做」，不能是「脚本写错」。脚本自身错误先修脚本——判据是它在空实现上打的是断言失败，不是 `Pattern is null` / `CommandNotFoundException` / 乱码（`.ps1` 含中文却没 BOM 时 PS 5.1 会按 GBK 解码，见 verify-harness §2）。
- 一条命令 + 退出码 + 一行摘要。不要靠人肉看日志判断。
- 判据分级、脚本模板、退出码陷阱见 skill `verify-harness`。

没有可执行的验收就进入实现 = 许愿变许瞎。

## 阶段 3 · 最小实现

**执行者**：默认**本会话自己写**。派子代理只有一个理由——买到独立的判据解释权，或在 ≥2 个互不重叠写域并行省墙钟；判据体量 ≥ 实现、实现 <30 行时，派发的固定成本（冷前缀 ≈58k + 交接）纯亏。派不派只看阶段 3.5 那张表，别按「分派表有几行」推断。

- 只做让**第一条验收变绿**的最小改动，别一次铺满全功能。
- 一次动一个关注点：先让它跑起来，再让它对，最后让它好看。
- 同一文件第 3 次 `edit` 失配 → 整块 `write` 覆盖（文件 <80 行），或先 `read` 出唯一锚点再 `edit`；确需批量替换时用 pwsh 脚本，但必须在同一步断言命中数 = 期望值（`(Select-String … ).Count -eq N`），不等就回退重来。
- 任何 `edit` 前该文件必须已 `read`（注入的 AGENTS.md / NOTES.md 不算读过）。
- 源码只用 `write`/`edit`，禁止用 shell 重定向写源码（编码、BOM、换行会坏）。
- **少 AI 味**：注释只写代码本身看不出来的东西（为什么这么写、踩过的坑、外部约束），不复述函数名/参数/流程；不写 `// TODO: 实现` 占位、不写 `// 1. 获取用户 2. 校验` 这类目录式注释、不写 emoji 分节、不写 "Here we ..." 式叙述；命名用业务词不用 `doHandleData` 一类空壳名；mock/演示数据单独放并标注，绝不留在交付路径上；能不写的注释就不写。

## 阶段 3.5 · 扇出编码（`subagent`）

愿望拆成几块**互不重叠**的编码活时，派子代理能省墙钟；但每次派发 = 一次冷前缀 + 一份任务书。**派不派只看这张表**（persona 不再另设阈值，两套判据一定打架）：

| 条件 | 处置 |
|---|---|
| 写域 ≥2 且互不相交，每块 >30 行或跨文件或要跑构建 | 派，一域一子智能体（互不依赖的几条在同一消息里发起） |
| 跨 ≥3 写域，或预计 ≥2 轮试错 | **必须派**——试错是子代理唯一不可替代的产出 |
| 判据体量 ≥ 实现（一次能过），或实现 <30 行一次 `edit` 能完 | 自写，SPEC 的「实现者」记「本会话（预算例外）」 |
| 几块耦合在同一批文件，或要主会话上下文才能推断 | 自写或串行，不并行 |

**单愿派发上限 4**（深度 1 ≤3 + 深度 2 ≤1）：`maxDepth: 2` 是能力上限不是配额，深度每加一层 = 再一次冷前缀 ≈58k input + 一份任务书。第 5 片起一律串行或由父会话自写；判据是"这一片能不能和已有的片并行且互不相交"，不是"还能再开一个"。

派发划不划算有实测（`.research/probes/T6-three-segment.md`，同一任务三次）：实现 115~130 行 / 判据 101~115 行 ≈1:1 时，派子代理 ≈$0.0100 / 8 请求（含 34,863 冷前缀），自写 ≈$0.0039 / 4 步——**派发更贵**，买的是「判据解释权不在实现者手里」与并行墙钟，不是省钱。

跨路由：policy 由 profile 层 `subagent-model-selection-settings` 写入（白名单 pro/flash），写入路径单测过、端到端无实测收益（r3 曾试图派 flash 被拒，白烧 3 步）——不传 `provider`/`model` 继承父路由最稳。

派发的成本 = 冷前缀 + 交接 + 实现段按**当前会话路由**计价，与判据体量无关。**判据与实现 1:1 且一次过的任务，派发是净亏**——省下的不是 token，是"不会偏袒自己代码"的那份保险，而这份保险在"验收比实现难写"时最不值钱。

**任务书八项，缺一不可**（子代理是全新上下文，只继承预设的 persona/技能/工具，不继承对话）：

1. **目标**：一句话，做完之后「谁看见什么」。
2. **写域**：允许改的路径白名单 + 「其他只读」；点名哪些文件归它，别和并发的另一块重叠。
3. **现有事实**：工程根、构建/验收命令**原文**（含 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File`）、环境坑（PATH 里可能没有 `node`，给绝对路径；BOM；退出码别用 `cmd; echo EXIT=…` 洗掉）。让它照原文跑，不自己猜。
4. **已完成到哪**：父会话已做的部分（`文件:行`），避免重复实现或覆盖。
5. **只做一件**：下一步只做哪一件事 + 步数上限（如 ≤15 步）+ 一句「本层能收尾就收尾，要再派按阶段 3.5 那张表判、并把理由写进回报」。
6. **完成判据**：哪条命令退出 0 算完 + 回报格式固定三行（改动 / 验证 / 残留）。

7. **模型（写在调用参数里，不写进任务书正文）**：不传 `provider`/`model` 就是继承父路由；要换实现模型就按白名单**顺序**分派——首选排第一（出厂默认 `deepseek-v4-pro` → `deepseek-v4.1-flash`），首选被拒（`child LLM route ... is not allowed for this Session` 或服务不可达）就顺延下一条，列表用尽再继承父路由。`provider` 与 `model` 两个必须一起传，白名单外的路由仍报 `child LLM route ... is not allowed for this Session`。没记录 policy 的旧会话别点菜，直接继承。
8. **开工规划（先回规划，再动文件）**：子代理的第一条回复以「计划：」开头，≤8 行——①做什么：对应哪条 AC、哪一行 SPEC；②用什么工具/命令（构建、verify、探测的具体命令行）；③要不要再下派（默认不派，写理由）；④改动哪些已有文件、新建哪些文件；⑤取舍与缺点：为什么这样做、代价是什么、被否掉的方案一句；⑥自检点：改完自己先验哪几条。这一段是 persona「不列计划」的明文例外；先改代码后补规划 = 返工。规划里只列本任务的活，不列「顺手优化项」。**规划写完不要停**：规划与实现同一轮内接着做，做完再回报；只交规划 = 零交付，而六个数里看不出这一刻（2026-11-21 W1 回放：子代理首轮只出规划，`errorSteps=0`、`interventions=0`、turn 记为 completed，文件根本没建）。

派发要点：

- 一次调用派一块；互不依赖的几块在**同一条消息**里一起发起，别串着等。
- 显式给 `cwd`（工程根），别让它继承你当前所在目录。
- 不轮询：发起后继续干自己那块（写总验收、复核不可变量），完成通知会自己回来。
- 深度 2 是**上限不是配额**：实测 4~6 文件的任务，领域子智能体都自判「任务书成本 > 写码成本」自己全写。别为了用上这层而切块。

**派发后守注意力（防走偏，与派发同等重要）**：

- **派出去就不再改需求**。任务书发出后，父会话新增的发现记进 `.wish/<slug>.md` 的「已知失败/补充」段，等这一轮收活再看要不要下一轮；塞第二条需求给正在干活的孩子 = 它两件事都做一半。
- **父侧等待期只做不冲突的活**：写总验收、核不可变量、查文档；不同时改同一批文件，不在等的时候给自己换方向（换方向 = 两份计划都在跑，最后谁也不是目标）。
- **每次收活先核三样**：`git status --porcelain -uall` / `git diff --stat` 对照任务书写域；验收指纹有没有变；回报是不是「改动/验证/残留」三行且在 AC 范围内。越界 = 回退越界文件再谈，别在越界的树上叠。
- **走偏的四个信号**：①改到写域外文件或动验收/SPEC；②顺手重构、升依赖、换目录结构；③把「做完这条 AC」扩成「顺便把整个模块理顺」；④回报里出现任务书没提的新功能。命中任一条，`send_message` 发一行纠偏包：`只做 <AC 原文>；写域 <路径>；其余改动回退；下一步只做 <一件事>`——不解释、不商量。
- **纠偏两次不动就接手**：连续 2 次纠偏仍越界/仍跑偏 → `interrupt_agent` 收尾，父会话自己改那 20%，或拆更小的写域重派。
- 子代理的规划（任务书第 8 项）与分派表对不上时先纠正规划，别让它先写完再返工。

收活：

- 子代理报绿不算绿 —— 合并后**父 agent 自己跑一次总验收**。
- 先 `git diff --stat` 核对它有没有越界改文件；越界就回退再谈，别在越界的树子上继续叠。
- 中断、半成品、同一错误复现 → 阶段 4.5。

## 阶段 4 · 循环

```
跑 verify → 只读第一处失败 → 改一处 → 重跑
```

- 失败输出只取关键行：编译取错误行（含中文「错误:」），测试取 failed 名 + 断言行，构建取 `BUILD FAILED` 前后 3 行。从 `$env:TEMP\wish-verify\<工程名>.log`（仓库外，交付不用清；若首行写 `TEMP unwritable` 说明沙箱不让写 TEMP，日志在 `<工程根>\.wish\verify.log`）用 `Select-String -Pattern 'BUILD FAILED|错误:|\[ERROR\]' -CaseSensitive` 取，别肉眼看全量。
- **三振法则**：同一处失败连 3 次，停手写一句「换法：X→Y」再动——这是你**唯一的一次换法许可**。换法必须换假设（换 API、换路径、换库、换设计），不是换个写法重试。换法后再连 3 次同点失败 = **二次三振**，按阶段 4.6 交回，不再自己试。
- 攒 3~5 处改动跑一条合并验证，不要每改一行跑一次全量构建。
- 成功跑过的命令不重跑；要确认状态就查产物文件时间戳。
- 版本/环境类失败先看事实：`node -v`、`java -version`、`where x`，别猜。

## 阶段 4.5 · 子任务中断就续，不重派

派发判据与任务书写法见阶段 3.5；这一节只管派出去之后停下来的情况。

扇出（`subagent`）之后，子任务可能中途停：返回里写「中断 / incomplete」、`list_agents` 里 inactive 却没有最终结论、产物写了一半（文件末尾截断、verify 没跑）、或者这次报的错和上次一样。

处置顺序，别跳步：

1. **先续，不重派**：`send_message({ agent: '<name>', message: '<断点包>' })`。子任务保留着自己的上下文；重派等于把探索重做一遍，还很可能撞同一个坑。
2. **断点包必含六项**（它自己的上下文可能已被压缩，摘要里未必还有这些）：目标一句话 / 已完成到哪（`文件:行`、已绿的检查）/ 卡点原文（报错那一行照抄）/ 下一步只做一件事 / 写域（哪些文件归它，别和别人重叠）/ 完成判据（哪条命令绿了算完）。只说「继续」等于让它猜。
3. **续两次不动就换法**：同一子任务连续 2 次 `send_message` 仍无进展 → `interrupt_agent` 收尾（别留僵尸进程），父 agent 自己接手，或拆小后重派一个写域明确的新子任务。这就是铁律 4 的三振在子任务上的形态。
4. **写域冲突就串行**：两个子任务动同一批文件 → 前一个交付后再派后一个；并行只在写域不重叠时成立。
5. **子任务的「我跑通了」不算绿**：合并时父 agent 自己跑一次总验收（`scripts/verify.ps1`）。子任务自报绿是假绿的第二大来源——它看不到别人的改动，也可能只验了自己那一块。

预算按段算，不按整场算：单段 >40 步或 >15 min 未见绿就交「已绿 / 红项 / 下一步」，别在原地续命；长任务按里程碑重置计数（整场几百步是常态，别拿 40 步当整场上限）。

## 阶段 4.6 · 三振之后：交回 Pro（别换写法续命）

三振法则管"换假设"；这一节管**用完那一次换法许可、仍不绿之后，由谁决定**。

实现段（子代理，或本会话自己）二次三振（同一点合计 6 次失败）→ 停手，按固定格式回报，不再自己试：

```
二次三振：<失败原文一行>｜已试：A/B（两次各换的是什么假设）｜怀疑：<你认为最可能的原因>
```

父（段 3，本会话）只做三选一，并写回 SPEC 的「已知失败」段：

1. **改验收**：判据本身错了（断言实现细节、假红、环境不可复现）→ 重写 `verify.ps1`，重算验收指纹，回段 2 从红重跑。
2. **换路线**：假设全错（API 不存在、库版本不兼容、设计走不通）→ 改 SPEC 的技术路线段；旧实现标「废弃」，别在它上面叠加补丁。
3. **亲自写**：方向对但细节密集（并发、编码、平台差异）→ 本会话直接改那 20%，其余仍交实现段。

**接管后仍不绿**（再 3 次同点失败）→ 停手交付，不原地续命：

```
改动：<已绿到哪>
验证：<当前 verify 的失败原文一行>
残留：<红项 + 怀疑方向 + 建议下一步（换方案 / 补环境 / 人工决策）>
```

## 阶段 4.7 · 验收（段 3）

实现段报完成后，**不由实现者宣布绿**，也不由 lead 自己宣布绿：**默认派一个只读验收子代理**（任务书只给四样：SPEC 路径、AC 清单、写域、报告路径；一句「只读：不改源码、不改验收、不装依赖」）。理由：验收买的是「判据解释权不在写代码的人手里」——同一个上下文自审，指纹只防「改判据」，防不了自己对自己宽容。

**豁免（本会话自验，但仍要「先写死预期输出再跑」）**：只改 1 个已有文件、没新建文件、没派实现子代理。这种任务派一次验收 = 冷前缀 ≈58k，比风险贵。

验收子代理按 `acceptance-verifier` 三步跑（指纹 → 逐条 AC → 越界），产出报告与结论。多写域并行时**逐域验收**：哪一域打回只回退该域，别把别的域一起推翻。

**质量评审是另一双眼睛**：AC 验收只回答"判据过没过"，回答不了"这段代码值不值得留"。本轮新建 ≥1 个文件或 diff >50 行时，与验收**同一条消息**再派一个只读子代理，任务书四样：①读哪些文件（写域白名单，只读）②只看什么（重复实现、命名与分层、死代码、边界与错误处理、复述流程的注释）③只读声明，不许改任何文件 ④回报 ≤5 条，分「必改 / 可改」，必改 ≤3 条。必改项回阶段 4 修一轮再复验；可改项写进交付「残留」行。实现者自查不算评审；1 个已有文件的小改按上面的豁免不派。

**验收必出测试报告**（段 3 的交付物，没有报告 = 验收没做完）。落 `<项目根>/TEST-REPORT.md`——固定名、git 可见、slug 写进标题，这样阶段 5.5 清理不会把它连着 `.wish/` 一起删掉（用户给了别的路径就用它的）。五段格式（改动 / 测试 / 过 / 没过 / 未覆盖）以 `acceptance-verifier`「测试报告」为**唯一权威**，这里不重复维护。

- 报告是**证据汇总**，不是叙事：每行一个断言，带命令和输出关键字；不许出现「功能正常」「已优化」这类不可判读的措辞。
- 用户明确要「测试报告」时，报告本身就是要交付的东西——回复里给 5 行精简版（改动 N 处 / 测了 N 条 / 过 / 没过 / 未覆盖），完整版落盘并 `present` 给用户；这是三行交付的合法例外（persona 输出行已明文开这个口子）。
- 全绿也要出报告（第 4 段写「无」）；有红项则报告 + 三行交付一起给，把红项原文照抄。
- 交付三行的「验证」行引用报告路径，别把整张表贴进回复。

## 阶段 4.8 · 功能测试一轮（段 4）

验收绿 ≠ 功能可用。跑一轮端到端：

- 构建 → 启动 → 3~5 条主路径，其中至少一条错误路径；
- 证据取命令输出 / HTTP 码 / 日志事件 / 截图 / uidump，一条命令打印 `EXIT=`；
- UI 类截图只当证据，判据是元素存在 / 文本相等 / 请求 200。

功能测试红 = 整体未完成，按阶段 4.6 交状态。**两关都绿才进阶段 5。**

## 阶段 5 · 交付

**入口条件：阶段 4.7 放行 + 阶段 4.8 通过，缺一条不进这一步。先跑阶段 5.5 清理，三行在清理之后才发。**

回复只留这些：

```
改动：<文件:行> — <≤10 字理由> ｜清理：删 N 留 M（<留下的判据资产>）
验证：<命令> → <结果一行>
残留：<没验到的 / 需真人真机的 / 已知限制>
```

- 没跑过的检查，不许写「已验证」。
- 许愿产出是**独立文件**（文档/视频/图片/表格/报告）→ 用 `present` 交付给用户（附路径与一句话说明）；纯代码改动留在工作区，不 present。
- 交付前自检：
  1. SPEC 每条验收都跑过？
  2. 不可变量动过吗？（技术栈、目录、公开 API）
  3. 跑过阶段 5.5 清理了吗？删了几个、留了什么，写进「改动」行（没删就不写这一段）。
  4. 用户拿到手第一步能不能直接跑？（命令写清楚）

## 阶段 5.5 · 清理过程文件（交付的最后一步）

「做完了」包括现场干净：交到用户手上的工作区里，不该有你自己造的过程件。**这是硬门禁**——整体任务（含多轮子任务、多写域）收尾没跑清理，就不算完成，三行交付里必须给出清理数。清理不是 `rm -rf` 一把梭——先分类，再逐条删。

**按改动规模分档，别给小改套大流程**：本轮只改 1 个已有文件、没新建任何文件 → 不必跑三步清点，只要确认自己没留临时件；**没删东西就不用重跑验收**（铁律 5 的「删后仍绿」只在真删过时生效），三行也不必写清理列（见 verify-harness §7）。只要新建过文件、跨 3 个以上文件、或用过截图与 codegen → 走完下面三步。

| 类别 | 典型文件 | 处置 |
|---|---|---|
| 判据资产 | `scripts/verify.ps1`、`scripts/smoke.mjs`、`.wish/<slug>.md`、`TEST-REPORT.md` | **留**：交付三行的「验证」要引用脚本；SPEC 是可复跑的依据，`TEST-REPORT.md` 是用户要的验收结论（在项目根、不在 `.wish/` 里，清 `.wish/` 不会连累它） |
| 纯过程件 | `*.log`、`*.bak`/`*.orig`、截图 dump、一次性 codegen 脚本、`.tmp-*`/`scratch/`、注释掉的旧实现、试到一半的备用实现 | **删** |
| 用户资产 / 重建昂贵 | 源码、`node_modules`、`dist`/`build`/`target`/`.venv`、`.git`、用户原有文件 | **永不删** |

三条命令，别凭记忆：

1. **先清点，只打印不删**：仓库内 `git status --porcelain -uall`（**`-uall` 不能省**：不加时 git 把整个未跟踪目录折成一行 `?? .wish/`，根本看不出里面有哪些文件）；无 git 时只扫一层再下钻：`Get-ChildItem -Force | Where-Object Name -notin 'node_modules','dist','build','.git'`，然后 `Get-ChildItem -Force .wish,scripts` 这类候选目录。别用 `-Recurse ... -Exclude node_modules`：`-Exclude` 不过滤遍历，只过滤列出的项，实测 `-Exclude .git` 仍会把 `.git\hooks\*` 全打出来。对着上表逐行标「留/删」。条目上百行时先 `Select-Object -First 50` 看主干，别把整屏灌进上下文。
2. **核对绝对路径 + 归属**：每个待删路径先 `Resolve-Path`，确认①在本工程内 ②是本轮自己生成的 ③不属第三类。判定"是不是本轮自己造的"以**本轮对话与 SPEC 里出现过的路径**为准；清点结果里对不上号的（用户原有的未跟踪文件、`vendor/`、别人留下的脚本）一律不删，写进「残留」。任一条不确定 → 不删。
3. **逐条删 + 复核**：`Remove-Item -LiteralPath <路径> -Recurse -Force`（一条一个路径，不用通配、不用 `-Include`）；删完 `git status --porcelain -uall` 应只剩本轮改动文件，再跑一次验收命令 → 仍 `OK`。复核不是走过场：删掉 `src/` 里一个被 import 的文件，`verify.ps1` 立刻 `exit 1`（实测 `Cannot find module`），这就是它拦住「清理过头」的方式。

边界：

- 自己刚生成的过程件不用问（红线 1 管的是**用户已有数据**）；用户原有文件、别人（含子任务之外）的产物一律不动。
- **删完必须重跑验收**：删掉一个还被 import 的临时模块，「全绿」就成了历史，交付时是假的。
- 验收脚本的日志默认写 `$env:TEMP\wish-verify\`，本来就不在仓库里，不用清；别把它改回仓库内。若脚本首行写 `TEMP unwritable`（沙箱是 `workspace-write`，TEMP 在写域外），日志回落到了 `.wish\verify.log`，那就随 `.wish/` 一起清。
- `.wish/<slug>.md` 若用户没要求留档，连目录一起删，并在三行里说一句；`TEST-REPORT.md` 在项目根，默认留（它是交付物，别跟着 `.wish/` 一起删）。`.wish/` 建目录时就写一份 `.wish/.gitignore`（内容一行 `*`），用户仓库不出未跟踪噪音；别去改用户的根 `.gitignore`（那是改用户已有文件）。
- 交付三行的「改动」行末尾补清理数：`改动：src/a.js:12 修空值 ｜清理：删 3 留 2（verify.ps1、.wish SPEC）`。

## 阶段 6 · 沉淀（记忆三档：写之前先选档，别默认写常驻）

常驻档整份注入、**每请求重付**（1 KB ≈ 300 tok × 每会话请求数）。所以「记下来」不等于「写进 AGENTS.md」——写错档位比不写更贵。

| 档 | 位置 | 进上下文 | 晋升条件 |
|---|---|---|---|
| 草稿 | 会话内 / `.wish/` | 否 | 阶段 5.5 清理时删 |
| 候选 | 项目 `NOTES-YYYY-MM.md`（append-only、按月轮转） | grep 命中才读 | 同类坑第 2 次出现，或实测省 ≥5 步 |
| 常驻 | 项目根 `AGENTS.md`（硬预算 ≤60 行 / ≤8 KB） | 每请求重付 | 回放用例验证过 + 带 `verified:` |

- 条目一行一条、可 grep、带证据：`- [坑] 一句话 | ev:<命令或 文件:行> | verified:YYYY-MM-DD | hits:N`。**无 `ev:` 不进候选**——错记忆比没记忆贵，它会带着错前提做决策还显得权威。
- **读到就 +1**：阶段 0 grep 命中一条并在本次决策里用上了，就把该条 `hits:N` 改 `N+1`（同一条 edit 里顺手改，别单开一步）。`hits` 是"淘汰"的唯一凭据——没有它，90 天规则无法执行，只能靠感觉删。
- 冲突时运行时赢：运行行为 > 抓包 > 服务中的资产 > 配置 > 落盘状态 > 源码 > 注释。
- 纠正写 `superseded-by:`，**不删原条目**（整文件重写删掉过的记忆只能靠会话日志逐字恢复）。
- **读侧是动作不是愿望**：任务开始（阶段 0）按「技术栈 + 模块名 + 报错词」grep 项目 NOTES/CODE-MAP/AGENTS，只读命中行 ±3；不许整份读（>15 KB 用 `offset`/`limit`）。
- 常驻档满了先淘汰：超 90 天未命中的移 `NOTES-archive-YYYY.md`，再腾位置。跨项目事实才进 AGENTS.md，项目细节留在项目自己的 NOTES。
- 不改 persona、不改技能，除非用户要求。

## 常见退化与对策

| 退化 | 症状 | 对策 |
|---|---|---|
| 先说后做 | 回了一大段「我将要实现…」然后没动 | 计划超过 3 行就落盘成 SPEC 文件，回复里只留一句「按计划执行」 |
| 假绿 | 把「代码写完」当验收通过 | 只认命令退出码与断言输出；没有就补，不许口头通过 |
| 范围蔓延 | 顺手重构、顺手格式化、顺手升级依赖 | 一次只改一行 SPEC 对应的东西；想顺手做的记进「非目标之外」，交付时问一句 |
| 整文件重写 | 每次改动都 `write` 整个文件 | 优先 `edit` 唯一片段；整写只在重构或文件 < 80 行时 |
| 反复试探 | 同一条命令换个写法试 5 次 | 三振法则；第 3 次去读 `node_modules/<pkg>` 里的 README 与类型定义、`<tool> --version` 实测、或报错码原文（本机无联网检索） |
| 交付即失联 | 说完了但没给怎么跑 | 固定三行：改动 / 验证 / 残留 |
| 现场不干净 | 交付后仓库里多出 `verify.log`、`*.bak`、截图、`.wish/` 里的草稿 | 阶段 5.5：先 `git status --porcelain -uall` 清点，逐条删，删完重跑验收；顺手把日志挪到 `$env:TEMP` |
| 过度提问 | 每个小选择都来问 | 只有红线三问；其余写「已假设」，用户不满意会自己说 |
| 为并行而派 | 单文件小改也开子代理，冷前缀 + 任务书比自己做还贵 | 只按阶段 3.5 那张表判；写域重叠一律串行 |
| 实现段改验收 | 跑不绿就去调 `verify.ps1`，改到自己绿 | 验收指纹核对；被改过 = 本段作废，回段 1 重写判据 |
| 跳段派活 | 需求还没转译就 spawn 实现子智能体 | 先出需求卡 + 分派表；没有写域白名单的子智能体必然改到同一文件 |
| 派后改需求 | 子代理干到一半又被塞进新需求/换了写域，两件事都做一半 | 新发现写进 SPEC「补充」段，本轮不追加；纠偏包一行，两次不动就接手 |
| 无报告交付 | 说「验收通过」，却拿不出改了什么、哪些没过 | 段 3 必出项目根 `TEST-REPORT.md`（五段见 acceptance-verifier），红项照抄原文 |
| 自己验自己 | lead 一边写一边判绿，或子智能体报「绿了」就当完成 | 段 3 换上下文（只读验收子代理）；豁免只在单文件小改时，且先写死预期输出 |

## 自检清单（交付前逐条过）

- [ ] SPEC 存在，且验收是可执行命令
- [ ] 验收曾经红过，现在绿
- [ ] 不可变量没动
- [ ] 新增依赖 = 0（或已在 SPEC 里写明）
- [ ] 阶段 5.5 已跑：过程件删了、判据资产留了，清理数写进「改动」行
